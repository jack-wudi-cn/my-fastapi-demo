# 产品需求文档 (PRD) - Invoice-AI MVP

**文档版本**：v0.1.0
**对应 MRD**：v1.0.0
**主导角色**：产品经理 (PM)
**参与角色**：开发 (Dev)、测试 (QA)

## 1. 业务背景与目标
构建一套“发票智能提取与校验”后端服务。解决财务手工录入慢、易出错、重复报销难查的痛点。核心目标是实现“自动提取 -> 规则校验 -> 异常拦截 -> 人工复核”的闭环。

## 2. 用户故事与验收标准 (User Stories & AC)

### US-001：异步提交发票
**As a** 业务前端系统，**I want to** 提交发票文本并立即获得回执，**So that** 页面不会因为等待 AI 处理而卡死。
- **AC 1.1**：提供 `POST /api/v1/invoices` 接口，接收包含 `raw_text` 的 JSON 请求体。
- **AC 1.2**：接口必须在 200ms 内返回 `202 Accepted`，并在响应体中包含任务 `id`。
- **AC 1.3**：接口收到请求后，将记录存入数据库，初始状态为 `PENDING`，并在后台启动异步任务。

### US-002：发票信息智能提取
**As a** 系统，**I need to** 从用户提交的乱糟糟的文本中，提取发票号、金额和日期，**So that** 转化为标准的结构化数据。
- **AC 2.1**：优先使用正则表达式（Regex）进行提取。
- **AC 2.2**：如果正则提取失败（例如文本格式乱码），系统必须自动降级，调用大模型（Mock 模拟）进行兜底提取。
- **AC 2.3**：如果正则和 LLM 都提取不到发票号，任务状态变为 `FAILED`，并记录错误日志。

### US-003：业务风控校验
**As a** 财务风控系统，**I need to** 对提取出来的数据进行自动核对，**So that** 拦截高风险单据。
- **AC 3.1**：如果提取的金额大于 10000 元，系统标记 `is_large_amount = True`。
- **AC 3.2**：如果提取的发票号在数据库中已经存在，系统标记 `is_duplicate = True`（防重复报销）。
- **AC 3.3**：提取与校验完成后，任务状态自动变为 `REVIEWING`，等待人工处理。

### US-004：人工复核闭环
**As a** 财务专员，**I want to** 看到系统的提取结果和预警信息，并进行最终裁决，**So that** 确保数据绝对准确。
- **AC 4.1**：提供 `GET /api/v1/invoices/{id}` 接口，用于查询提取详情。
- **AC 4.2**：提供 `POST /api/v1/invoices/{id}/review` 接口，接收审核动作（`APPROVE` 或 `REJECT`）。
- **AC 4.3**：只有状态为 `REVIEWING` 的单据才能被审核。审核通过后状态变为 `APPROVED`，驳回变为 `REJECTED`。

## 3. 功能边界 (Scope)
- **包含**：API 接口、状态流转、正则提取、Mock LLM 兜底、并发防重。
- **不包含**：前端 UI 界面（仅用 Swagger 测试）、真实 OCR 图像识别、真实 LLM API 调用（为了省钱，用 Mock 写死数据）。

## 4. 非功能性需求 (NFR)
- **幂等性**：基于 `raw_text` 的 MD5 哈希，5 秒内重复提交相同文本直接返回上次结果，不重复创建任务。
- **并发控制**：数据库层对 `invoice_number` 建立唯一索引，防止并发导致的重复入库。
